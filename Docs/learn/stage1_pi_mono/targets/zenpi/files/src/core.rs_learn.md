## Structure and ownership

`WorkerExecutionBinding`, `Turn`, `TurnInputRequest`, `TurnSubmission`, `AgentPhase`, `AgentEvent`, `AgentSnapshot`, and `CompactionReport` define the public state and correlation contracts. `AgentError` is the typed failure surface. `Agent` owns the session journal, backend, history, active turn, input queue, model/reasoning/persona selection, attachments, approval coordinator, resources, extensions, tool recovery, live-owner mailbox, and recovery acknowledgements. `RunMode`, `CliOptions`, and `CliCommand` are the process boundary shared by TUI/headless callers and the CLI parser.

## Admission and turn lifecycle

`submit`, `start_or_steer_turn`, `start_turn_if_idle`, `steer_turn`, `start_new`, `steer_existing`, and `start_reissued` make admission explicit. A rejected request returns `NotSubmitted` and does not append a turn or call the backend. `run_active_turn_cancelable_with_events` drives provider streaming and publishes bounded progress; `complete_with_tools` linearizes tool calls, approvals, output capture, recovery records, and final journal writes. `release_turn_concurrency` closes the active-turn gate. `process*` wrappers provide synchronous and cancelable convenience paths while preserving the same admission semantics.

## Project, owner, and recovery boundaries

`prepare_project_with_options`, attachment workspace setters, live-owner registration/heartbeat/unregister, mailbox claim/finish, `resume_session`, `replace_session_with_commit`, `try_close`, and `close` are the lifecycle hooks used by project workspace and headless hosts. Owner epochs and revision checks prevent stale asynchronous events from mutating another project. Resume is committed atomically; failed replacement leaves the previous live agent and journal usable. `acknowledge_recovery`, `operation_recovery`, `resolve_operation_recovery`, and `resolve_tool_outcome` expose explicit recovery instead of silently retrying side effects.

## Model, reasoning, context, resources, and extensions

`set_model`, `set_reasoning_effort`, `restore_model_selection`, `model_status`, `set_context_budget`, `compact_context*`, `configure_extensions`, `publish_extensions`, `configure_resources`, `restore_resources`, `reload_resources`, and `set_skills` keep provider capability and resource snapshots owner-bound. `prepare_semantic_provider_context` and `context_source_for_provider` select history/checkpoints within the configured budget. Resource reload is cancelable and preserves the old catalogue on failure; extension leases are prepared and published only after validation.

## Tools, approvals, and side effects

`set_tools_with_resources`, `set_approval_policy`, `set_worker_execution_binding`, `admit_blueprint_worker`, `settle/renew/cancel/expire_blueprint_worker`, `external_evidence_control`, `run_user_shell_with_cancel`, `prepare_tool`, `invoke_tool`, `persist_tool_invocation`, and `finish_tool_result` enforce tool context, policy, budgets, workspace roots, and cancellation. Unknown tool outcomes and artifact output cleanup use journal receipts so cleanup can be retried without double-counting. `tool_output_control`, `read_tool_output`, and `cleanup_tool_output` expose bounded output access and receipt verification.

## CLI and process boundary

`parse_args`, `make_backend`, `backend_from_effective`, `print_help`, and `run` keep mode selection, backend configuration, session paths, headless JSONL, and TUI startup at the binary boundary. The file deliberately has only `RunMode::Tui` and `RunMode::Headless`; no hidden daemon is created here. IDs and provider idempotency keys are generated by `next_id`, `tool_operation_id`, and `provider_idempotency_key`.

## Zenpi-to-pi-mono mapping and gaps

The file supplies Zenpi's single-agent owner equivalent for pi-mono's turn loop, compaction, model registry, tool execution, recovery, and session persistence. Zenpi adds explicit project/owner epochs, approval policy, bounded artifacts, staged resources, blueprint worker governance, and headless/TUI mode separation. The remaining integration work is cross-file: project workspace must route every TUI/headless request through the owner methods above; receipt acceptance must be based on current hashes and independent runtime evidence; and `core.rs` itself does not prove real PTY behavior or UI rendering. Those claims belong to the UX and host validators and are not inferred from this file.
