# feat: 账号体系（OAuth / apikey / 别名）+ plan 模式 + goal 模式 + compact 增强

## 概述

本文提出四类能力，尚不表示实现或验收完成：统一账号登录体系、
Plan 流程引导、成果 OKR 驱动的 Goal，以及 context compact 增强。
Goal、Flow 和运行时交互以
[详细功能契约](feat-goal-flow-intervention.md) 为准；本文保留功能入口，
执行条目和状态由蓝图统一维护。本 PR 只修改文档。

## 功能一：账号体系

### 新增命令

- `zenpi config auth list [--json]`
  列出所有已配置的 agent 账号：别名、provider、base_url、
  认证方式（apikey / oauth）、是否默认账号，凭证全程脱敏。
- `zenpi config add auth codex [email]`
  通过 OpenAI OAuth（ChatGPT 账号）浏览器授权登录；传入 email
  作为登录提示与账号别名，例如
  `zenpi config add auth codex lzjaaaaa@gmail.com`。
  授权凭证持久化后自动刷新，失效时提示重新登录。
- `zenpi config add auth apikey <base_url> <provider> <apikey> [--alias 别名] [--json]`
  非交互式添加 API Key 账号。
- `zenpi config import-codex --profile codex` 增强
  除 API Key 外，现在也能识别并导入 Codex 的 OAuth 登录凭证。

### 影响

- 所有账号（apikey 与 oauth token）统一持久化到
  `~/.zenpi/auth.json`，文件权限保持 0600；旧格式配置无缝兼容。
- 每个账号有唯一别名，别名即 profile，切换账号沿用现有习惯。

### 效果

- 用 ChatGPT 账号（Gmail）登录的用户不再需要手动管理 API Key。
- 多账号、多 provider 集中管理，一目了然，随时切换。

## 功能二：Plan / DAG 流程引导

### 新增能力

- `/plan [instruction]`：独立生成计划提案，不隐式创建 Goal。
- `/goal plan [提示词]`、`/goal dag [提示词]`：都是 Flow 的提示词预设，
  分别引导顺序步骤和依赖分析，不创建第二个执行引擎或调度器。
- 已有 Goal 时，只读 fork 当前任务的已提交上下文生成提案，主线继续。
  返回内容走与普通提示词相同的 steer 入口，默认在任务边界交付。
- 简单任务用 Plan；复杂子任务可局部展开 DAG，保留外层计划与已完成进度。
  同范围应用新版本才替代旧引导；不同请求不因返回顺序被静默丢弃。
- 新 Goal 默认先理解目标、提出 KR 和计划，确认后才执行；已有批准范围内的
  细化不阻塞无关工作，改变目标/KR、预算或权限须重新确认。

### 影响

- 计划阶段禁止实现性副作用，允许受控只读调查及宿主持久化日志；
  不写工作区、不执行命令、不递归委派，执行仍受审批和预算约束。
- TUI 和 headless 使用相同的类型化命令与核心入口。

### 效果

- 规划可以在不中断主线的情况下细化，提案保留来源、适用范围和过期检查。

## 功能三：goal 模式

### 核心语义

- `/goal <目标>`：创建持久化 Objective 与可验收 KRs；Blueprint 关联可选。
  默认理解、拆解、确认后推进。Goal 管成果，Flow 管过程提示，Runtime 管执行。
- 自动续行只能在运行时完全收束后发生一次；等待确认、外部事件、预算或真实
  阻塞时暂停，不靠反复调用模型空转。完成必须逐 KR 验证证据，不能以摘要、
  控制面回执或预算耗尽替代成果。

### 控制命令

- `/goal`、`status`、`list`、`supervise`：只读查询，在项目内展示进度，
  不新增功能型顶层标签页，不调用模型。
- `/goal approve [版本]`、`edit <目标>`：确认提案或显式修改目标；
  确认计划不等于授予工具权限，headless 必须带预期版本。
- `/goal steer <内容>`：显式即时引导；根范围引导逐分枝记录交付回执，
  不承诺修改已发出的请求，也不回滚已发生的副作用。
- `/goal pause`、`stop`、`resume [id]`、`cancel`、`clear`：暂停、恢复、
  取消或解除当前绑定；保留进度和历史，不删除文件。
- `/goal rebuild <节点>`：先停止并核对旧尝试，再重做受影响部分；
  下游证据按依赖失效，不重置无关成果。
- `/goal rollout --force`：请求最简剩余路径和摘要，不降低 KR，不绕过验收。
- `/goal handoff <节点>`：接收方确认后才转移执行权，不允许双重写入所有者。

### 执行中的交互

- Goal 或普通 TUI 执行中，Enter 提交提示词默认等待当前 task 结束；
  没有 task 则等待当前 KR，再无 KR 则等待当前执行轮结束。
- 第一次 Esc 将编辑区提示词即时提交；编辑区为空则提升选中的待交付项，
  未选择则提升最早一项。第二次连续 Esc 停止当前根执行及其子任务、规划 fork。
  弹窗 Esc 只关弹窗；拒收保留草稿；键盘自动重复不计为第二次。
- 精确输入 `continue` 或 `继续` 从当前中断点恢复，保留预算用量和待交付输入；
  无检查点明确拒绝，清理未完成则只保留一个恢复意图，不重复启动。
- `/goal plan [提示词]` 和 DAG 的 fork 提案也遵循上述交付方式。
  结果未就绪时第一次 Esc 标记为就绪后即时交付，不提前注入空计划。

### 影响

- 持续执行不等于失控：设有轮次/时间预算上限，超限自动暂停；
  全程受现有审批与权限体系约束，不绕过任何工具确认；
  用户可随时通过 steer / rebuild / rollout 或叫停介入。
- 只有根宿主可在受限预算、路径和权限内创建有界子执行，子执行不能递归派生。
  DAG 不隐式开启并发；模型切换只影响后续请求，运行中子任务保留配置快照。

### 效果

- 目标可验收、过程可引导、进度可恢复；规划不会覆盖已有成果。

## 功能四：compact 增强

### 新增能力

- compact 配置：可在配置文件中设定自动压缩阈值、保留轮数、
  默认压缩提示词。
- `/compact --force`：强制立即压缩，无需等待阈值触发。
- `/compact [提示词]`：压缩时附加额外指令（如"完整保留迁移
  方案""额外参考某文档"），指导压缩保留重点内容。

### 影响

- 压缩行为从"固定不可控"变为可配置、可强制、可引导；
  附加提示词随压缩记录留存，便于审计。
- compact 前持久化进度和交付状态；后续请求从权威记录重新注入 Goal/KRs、
  当前 Flow 和任务检查点，而不是依赖有损摘要记忆。未到交付边界的提示词不
  提前注入，停止的 Goal 不自动复活；压缩失败保留最后有效检查点。

### 效果

- 长会话压缩后关键信息不丢失，压缩时机和策略由用户掌控。

## 验收标准

- [ ] 三条 auth 命令可用，凭证脱敏，auth.json 权限 0600 且旧格式兼容
- [ ] import-codex 能导入 OAuth 凭证且重复执行幂等
- [ ] /plan 与 Goal 默认规划允许受控读取，但确认前不产生实现性副作用
- [ ] Goal 按 KR 验收，自动续行有收束边界，超限/中断不误报完成
- [ ] Plan/DAG 使用只读 fork 和同一交付入口，晚到提案不覆盖进度
- [ ] Enter 延迟交付、两次 Esc、continue/继续在 TUI/headless 等价且可恢复
- [ ] supervise 不干扰执行；steer、停止、模型切换和子执行具有真实回执
- [ ] rebuild 只重做受影响分枝；rollout 不绕过成果验证
- [ ] handoff 移交外部执行，进度可跟踪，重复移交被拒绝
- [ ] compact 可配置、可强制、可附加提示词，正确恢复 Goal/Flow/交付状态
