## 2. 现状事实（已核实，带 `file:line`；不要重新推测）

**内核形态**

- 单 crate，**同步内核，无 async/tokio**。一个正在执行的 turn 占用一个 OS 线程，
  阻塞在 `Condvar`、provider I/O 或子进程上。
- 整个回合期间**持有** `Arc<Mutex<Agent>>`。`src/headless.rs:4499` 的注释明确要求
  "Keep the agent lock until its events are copied into this"。
- `owner_handles()` 只枚举项目 owner，**不含 arch owner**（`src/project_workspace.rs:684`）；
  `arch_agent()` 创建时还要 `active.lock()` 读 session/cwd（`src/project_workspace.rs:639`）。
- 每个 owner 拥有：自己的协调器、自己的 `SessionStore`（一个 journal 文件）、自己的配置快照。
- `governance` 里 `Processes` 是**累计启动预算**（已发生的消耗，不因任务结束退款），不是"当前活跃进程数"。

**调度**

- `BackgroundRunner`：**单一活动槽 + 有界 pending**。
  `src/runtime.rs:454-455`：`let mut active: Option<Active<O, E>> = None; let mut pending = VecDeque::new();`
  模块注释（第 17-18 行）原文：*"submitted while a job is running become pending follow-ups and are
  started in FIFO order after the active job reaches a terminal result."*
  只在 `active.is_none()` 时启动新任务（`src/runtime.rs:545`）。
  **排队有界**：`max_pending` 默认 `32`（`src/runtime.rs:119`），满了直接拒绝。
- 有界的并行工具批已存在（`tool_runtime`），有源顺序结果归并、取消传播、
  以及"未知/修改型工具整批转串行"的规则。

**审批等待**

- `src/approval.rs:242`：`wake.wait_timeout(state, Duration::from_millis(50))` —— **50ms 轮询**。
- `src/core.rs:5364` 把 `&|| pump.poll(is_cancelled())` 作为取消谓词传给协调器，
  而审批循环在**持有 `CoordinatorState` 锁时**调用它（`src/approval.rs:225-235`）；
  `InputPump::poll` 会 `port.service(&mut session, ...)`（`src/input_queue.rs:849`）。
  **即：会话输入服务发生在协调器临界区内。**
- `has_pending()` 在 mutex poisoned 时返回 `true`（fail-closed）。

**传输**

- headless 是 stdin/stdout JSONL。`ReplayState`（`src/headless.rs:133-153`）已经有：
  `owner_epoch`、`next_sequence`、`acknowledged`、`replay_floor`、`terminals`、`in_flight`、
  `completed`、`unknown`，以及 `journal: Option<ReconnectJournal>`（一个传输 WAL）。
- 宿主循环里有直接 `write_all` / `flush`。

**其它**

- TUI 是单屏客户端；headless 设计上可被管道组合（README 把 headless 定位为轻量进程）。

## 6. 10,000 下才出现的新失败模式

请逐条给"检测手段 + 处置策略"：

1. **一个 owner 的 mutex poisoned**，在 1 万个 owner 的进程里怎么处置？杀掉整个进程的代价多大？
   能不能只报废那一个 owner？
2. **一个线程 panic** 在 10k 下如何隔离？会不会带走整个进程？
3. **fd 耗尽**发生时，正在执行的 turn 会观察到什么？如何 fail-closed 而不是 fail-open？
4. **惊群 / 唤醒风暴**：10k 个等待者在同一事件上被唤醒。
5. **journal 写入卡住**（磁盘满、fsync 慢、NFS），会不会把一个 owner 的问题扩散成全进程？
6. **事件缓冲 OOM**：某个客户端不读，缓冲增长到多大才算失控？淘汰策略是什么？
7. **取消风暴**：10k 个同时取消，取消路径本身会不会成为新的串行点？
8. **审批风暴**：10k 个同时请求人工审批——这件事在人类层面可解吗？
   如果不可解，系统应该怎么表现（拒绝？降级？限流？）——请给判据。
