## 1. 核心结论

对上层明确提供一层独立的 **AccountScheduler**，统一承接账号分配、会话亲和、
配额准入、排队和结算。Goal、Flow、主会话、Subagent 和批量任务调用同一接口，
不能分别维护账号选择与配额逻辑。

抽象的目的不仅是复用，更是支持后续增加调度方法：固定机制与可替换策略分离。
新增方法只实现策略接口、注册配置与测试，不修改 Agent Loop、Provider 适配器、
认证组件或额度结算规则。现有五种策略是首批实现，不是封闭的策略枚举。

这层内部组合纯路由策略与现有 Quota Owner；后者仍是额度预留、结算和恢复的
唯一权威，不另建竞争账本。Provider Gateway 只组合调度端口、认证和协议适配器，
把统一请求转成厂商请求，再把响应还原为统一事件。它不自行轮换账号。

Broker 持久化账号绑定，Session 保存任务及绑定回执；Runtime 继续拥有执行、取消和资源回收。
Flow 只声明路由意图，不能用提示词代替配额算法或修改安全限制。
调度目标是减少不必要的缓存失效，而不是承诺本地能够控制远端 KV cache。

## 2. 当前组件与最小改造

| 当前位置 | 事实 | 改造方向 |
|---|---|---|
| `Cargo.toml` | Rust + ureq + serde，没有 JavaScript 模型 SDK 依赖 | 保持原生 Rust；同一二进制提供共享 Broker，不增加 JavaScript 桥接 |
| `src/backend.rs` | 已有 Backend、CompletionRequest、ProviderEvent；Responses 和非流式 Chat 适配 | 保留统一边界，逐协议拆分编码、流解析和能力验证 |
| `src/core.rs::make_backend` | 创建后端时解析一个 Profile；生产入口缺省协议为 Responses | 每次模型请求边界解析不可变路由快照 |
| `src/config.rs` | Profile、API Key、模型配置和导入基础；没有完整 OAuth 生命周期 | 增加账号身份、凭证引用、套餐、模型目录；兼容读取旧 Profile |
| `src/governance.rs` | 已有资源预留、结算与未知结果保留 | 扩展账号/共享额度维度，不建立竞争账本 |
| `src/runtime.rs`、`src/session.rs` | 有界执行、取消和持久化基础 | 复用任务所有权与恢复，增加路由与额度事件 |

库级协议枚举的默认值与生产入口不同，迁移必须清点调用点并增加默认行为测试。
模型目录目前主要来自本地配置，不能把可填写任意 model ID 当成已验证模型支持。

## 3. Provider 与认证范围

以下是目标接入清单，不是当前全部可用的承诺。厂商、套餐、地域和模型分别验收。

| 接入项 | 认证方案 | 协议选择 | 范围 |
|---|---|---|---|
| OpenAI API | API Key | Responses 为主，Chat 兼容 | 复用现有适配并补充能力测试 |
| ChatGPT/Codex 订阅 | 专用 OAuth 连接 | 专用认证/端点配置下的 Responses 适配 | 候选；确认授权方式与使用范围后接入，不能向任意 Base URL 转发 Token |
| OpenCode Zen | API Key | 每个模型分别选择 Responses、Chat、Messages 或 Google | 目标内置 Provider；不能使用一个全局 wire_api 覆盖所有模型 |
| OpenCode Go | 套餐 API Key | 每模型选择 Responses、Chat 或 Messages | 目标内置套餐；会话头、真实客户端标识和套餐资格必须正确 |
| 火山方舟普通推理 | API Key | Chat、Responses，逐模型验证 | 目标内置 Provider；允许用户配置地域/推理接入点 |
| 火山 Coding/Agent Plan | 套餐对应 API Key | 独立套餐路由；优先核验 Chat，其余逐套餐确认 | 不继承普通推理端点；Responses、并发及批量资格未核验时禁用相应能力 |
| 阿里百炼普通推理 | API Key | Chat、Responses，按模型/业务空间验证 | 目标内置 Provider，地域和 Workspace 固定绑定 |
| 阿里 Coding Plan | 专用 API Key | Chat、Messages；不使用 Responses | 独立套餐定义；不准入无人值守批量池 |
| 阿里其他 Token Plan | 对应产品的专用凭证 | 独立产品配置 | 不是 Coding Plan 的别名，目录与使用范围另行验证 |
| OpenRouter | API Key 或 PKCE 换取 API Key | 首期 Chat；其他路由独立验证 | OAuth 首期明确候选，账单仍属于授权后的 API Key |
| Anthropic API | API Key | Messages | 目标协议适配；不内置第三方 Claude 订阅 Token 复用 |
| Google Gemini API | API Key | Google 原生 | 支撑 Zen 的 Google 模型；云工作负载身份另行扩展 |
| GitHub Copilot | 专用账号授权连接 | 按授权端点和模型决定 | 候选；模型权限、令牌交换及第三方接入资格是上线前置条件 |
| 自定义兼容服务 | API Key 或显式 no-auth | 用户指定的已实现适配器 | 不因为域名/模型名称看起来相似而自动赋予能力 |

OAuth 是登录方式，不是一个通用推理协议。授权完成可能得到可刷新 Token，
也可能得到长期 API Key；两者必须有不同生命周期。当前 zenpi 没有完成上述
OAuth 登录/刷新闭环。未核验的第三方 OAuth 不能列为已支持，更不能冒充官方客户端。

模型目录记录 `provider + product + region + upstream_model_id + protocol`。
用户的逻辑模型别名解析到一个版本化候选集合；同名模型跨 Provider 不自动视为同一版本。
目录可由受控刷新和本地覆盖形成，运行中快照不因远端目录更新而变化。

## 4. 统一协议边界

统一的是代码中的语义类型，不是把所有请求伪装成 `/v1/responses` HTTP：

```text
用户/Goal/Flow -> ExecutionIntent -> AccountScheduler.bind -> BindingHandle
BindingHandle + 规范化上下文 -> Agent Loop
Agent Loop -> 统一 ModelRequest -> Gateway
Gateway -> AccountScheduler.acquire -> RequestPermit 或等待/拒绝
RequestPermit -> Auth/编码准备 -> begin_dispatch 消费 Permit -> 厂商 HTTP/流
厂商 HTTP/流 -> Protocol Adapter -> 统一 ModelEvent -> Agent Loop
结束/失败/取消 -> AccountScheduler.settle -> Quota Owner + Session/Runtime
```

进入 Loop 前完成配置规范化和能力约束；每次实际调用前仍须重新检查账号可用性，
否则长任务期间的配额耗尽、Token 过期和用户切换无法生效。Loop 不读取厂商 JSON。

统一请求包括有序消息内容块、工具定义、工具调用/结果 ID、输出约束、推理选项、
上下文引用、请求 ID、使用上限和缓存意图。统一事件至少区分开始、文本增量、
可选受控推理块、完整工具调用、用量、成功、失败和取消；每次尝试只有一个终态。
工具参数流解析完成且验证成功后才交给工具执行器，禁止把半段 JSON 当作调用。

有效能力 = 模型声明与适配器实现、接入点限制、任务策略的交集。
不支持的参数应在发请求前拒绝，或按显式允许的降级策略生成回执，不能静默丢弃。
不可移植的 reasoning 签名、response ID、文件 ID 和缓存句柄留在带路由作用域的
私有扩展中；换厂商时不转发这些对象，也不把私有推理强行转换成普通提示词。

### 4.1 独立的账号分配与调度层

AccountScheduler 是共享 Broker 内的类型化调度边界；CLI 只持 BrokerClient，
不各自初始化账号池或 Provider 连接池。它不是第二个任务调度器，不拆解任务、不判断 KR
完成、不解析模型流、不执行工具。依赖关系仍由既有任务所有者管理。

**两种生命周期必须分开：**

1. `BindingHandle` 是长生命周期的账号/模型亲和引用，默认随 session/branch 保留。
   绑定本身不消耗请求次数，也不永久占用并发槽，更不保证未来始终有额度。
2. `RequestPermit` 是一次模型请求的短生命周期准入凭证，包含不可变路由与额度预留。
   每次工具续接、规划调用或重试都重新申请；Granted 仅代表已预留，
   必须再经 begin_dispatch 的持久化发送栅栏消费 Permit，才能实际发送。

`ExecutionIntent` 包含任务与会话身份、模型要求、可用账号池、可选固定账号、
调度策略、用途/数据边界、预算引用、截止时间和允许切换范围。上层不用提交密钥，
也不必知道每个账号的实时额度。Subagent 的要求必须与父任务授权范围取交集。

`BindingHandle` 对 Loop 暴露绑定 ID、模型能力、版本及执行 epoch；真实账号和
认证信息只在调度/发送边界解析。用户仍可通过脱敏回执看到实际选中的账号。
`RequestPermit` 包含 assignment_id、request_id、绑定版本、路由快照、
credential_ref、cache_scope、reservation_id 和有效期，不包含明文凭证。

| 对外操作 | 输入与结果 | 契约 |
|---|---|---|
| bind | ExecutionIntent -> BindingHandle 或拒绝 | 创建/恢复亲和绑定；同一幂等身份不会生成第二个绑定 |
| acquire | BindingHandle + 本次请求约束 -> Granted、Waiting 或 Rejected | 重新校验资格和预算，原子预留后返回唯一 RequestPermit |
| settle | permit_id + 本次尝试结果/用量 -> 结算回执 | 幂等结算，区分确知结束和未知远端用量；不伪造退款 |
| rebind | binding_id + expected_revision + 新要求 -> 新绑定版本或拒绝 | 显式切换和策略允许的自动迁移共用入口，拒绝陈旧修改 |
| cancel | task/binding/wait 身份 -> 停止准入回执 | 撤销等待与未发送准入，禁止新分发；已发执行仍由 Runtime 取消并核对 |
| explain | task/binding 身份 -> 脱敏决策快照 | 展示选择、排除、等待和额度来源，不调用模型 |

自动策略需要迁移时也必须经过 rebind 的身份、权限与版本检查，不能直接修改
共享 Profile。模型能力发生变化时先交回 Core 重建/验证上下文，再申请新 Permit，
不能让 Loop 按旧模型能力准备请求而实际发给另一模型。

等待返回的是可取消的稳定 WaitTicket，状态由同一个调度所有者维护，并投影为
Runtime 的 route-wait。容量释放、窗口恢复或配置变化唤醒它；重复 acquire 使用
原请求 ID 取得原等待/准入结果，不复制等待项。队列按条数与字节数有界。
这不是普通提示词的第二个干预队列，TUI/headless 不能在外层另做轮询调度。

准入、开始发送、执行结束和额度结算有不同事件。Gateway 在发送前校验 Permit
尚未过期、未撤销、版本匹配，并原子登记该 Permit 的发送开始。逻辑上只能消费
一次；进程崩溃导致无法确认是否已发送时保留 unknown，不承诺远端 exactly-once。
Cancel 和开始发送由同一准入状态串行判定；停止先发生则不能发送，发送先发生
则进入 Runtime 的取消/核对路径，不靠立即归还所有配额制造成功停止。

内部只保留最小分工，不把每种策略做成一个调度器：

- Account/Provider 目录提供资格与能力，Auth Owner 提供私有凭证解析。
- Policy 是对候选快照的确定性排序；pinned/sticky/spread/auto/remote 共用准入路径。
- Broker 内 Quota Owner 负责唯一共享计数、预留和结算，Session 保存绑定回执与执行关联。
- Runtime 负责实际任务生命周期和进程回收；Gateway 是唯一重试编排者，每次尝试
  仍申请新的 Permit，并计入原任务预算。AccountScheduler 本身不发模型请求。

建议以 `src/account_scheduler.rs` 承接这一公共边界和纯策略，扩展
`src/governance.rs` 的共享额度能力，在现有 Backend/Gateway 调用点接入。
这是后续实现的所有权建议，不是本轮增加第二套 Provider API 或运行时代码。

### 4.2 可扩展的调度策略接口

**机制固定，算法可换。** AccountScheduler 提供统一生命周期，AccountStrategy
只决定当前任务在合格候选中优先选谁、是否值得等待。算法无权生成 RequestPermit。

```text
AccountScheduler
  -> 资格与硬约束过滤
  -> StrategyRegistry.resolve(id, version)
  -> AccountStrategy.select(只读快照)
  -> 校验策略结果 + 原子预留
  -> RequestPermit / Waiting / Rejected
```

以下是概念接口，不是本轮已实现的 Rust API：

```rust
trait AccountStrategy: Send + Sync {
    fn select(&self, input: &SchedulingSnapshot)
        -> Result<PlacementDecision, StrategyError>;
}

enum PlacementDecision {
    RankedCandidates(Vec<CandidateId>),
    Wait { reason: WaitReason, until: WakeCondition },
}
```

快照包含本次需求、当前亲和绑定、合格候选 ID、脱敏额度观测、负载、缓存亲和估计、
策略配置和固定的决策时间。不含密钥、OAuth Token、完整会话正文或可变账本句柄。
返回的是候选排序或有界等待建议，不是直接分发命令。决定使用随机算法时，随机种子
也作为显式输入记录，不依赖隐藏全局状态，便于复现和解释。

策略由构造阶段校验参数；热路径 select 不进行网络、文件写入、模型调用或持锁等待。
负载统计与历史指标由宿主有界采集后注入快照，不让每个算法另建后台监控或配额数据库。
内置实现与可安装插件使用同一契约。默认保留受信任的 Rust 内置策略；可安装模式
使用显式启用、资源有界的 Wasm host，不引入原生动态库、任意脚本或额外插件服务。
安装、自检、热替换、回滚和隔离细则见
[账号分配与调度插件规格](feat-account-scheduler-plugins.md)。

Registry 以稳定 `strategy_id + 实现版本 + bundle 摘要` 解析实现和参数校验器，
另行校验 ABI 版本。下面省略安装时固定的摘要，仅展示策略配置：

```yaml
strategy:
  id: sticky
  version: "1.0.0"
  params:
    max_wait_ms: 3000
```

参数在配置边界完成结构化校验并构造策略实例，不在每次调度中任意读取 JSON。
未知策略、重复注册、未知参数或不兼容版本明确拒绝，不能静默退回默认算法。
记录实际策略版本、参数摘要、输入快照版本、候选排序及最终准入结果。
版本更新默认只影响新绑定；显式更新已有绑定时在安全准入边界切换策略引用，
运行中请求不变，已有账号绑定是否迁移仍受统一 rebind 契约限制。

比如后续增加 weighted-round-robin、least-loaded、deadline-aware 或 cost-first：

1. 增加一个 AccountStrategy 实现及其参数校验。
2. 在 Registry 注册稳定名称和版本。
3. 补齐共同契约测试及算法自身的确定性测试。
4. 用户或 Flow 在已允许的策略集合内选择它；其他模块无需增加对应分支。

策略可以改变软目标排序，但硬约束始终由宿主执行：模型资格、数据边界、套餐用途、
账号禁用、剩余额度、并发上限、取消与版本校验不会交给插件决定。
策略返回快照之外的候选、重复候选、无解释的空排序或越界等待时按类型化错误拒绝；
宿主重新验证过时快照，预留失败后有界重算或等待，不能按陈旧结果直接发送。
策略失败不能绕过准入、隐式切换付费方式或触发另一个算法的隐藏重试。

本接口只扩展**账号放置策略**。任务依赖、就绪任务顺序和实际执行仍由原所有者负责。
未来若确需改变任务队列顺序，应在任务所有者处增加独立的排序接口，而不是把所有
调度问题、DAG 执行和模型循环塞进 AccountStrategy。

## 5. 最小数据模型

| 对象 | 核心字段 | 不承担的职责 |
|---|---|---|
| ProviderSpec | 产品、地域、端点、模型目录版本、协议和能力 | 不保存原始密钥 |
| Account | 稳定 account_id、别名、身份、credential_ref、quota_group、可用状态 | 不等于某一个模型 |
| AccountPool | 允许的账号集合与数据边界 | 不创建智能体 |
| RoutingPolicy | 指定模型/账号、策略 ID/版本/已验证参数、切换条件、用途、预算、并发和等待上限 | 不执行自然语言流程 |
| SessionBinding | session/branch、账号、模型、接入点、缓存作用域、绑定版本 | 不永久占用请求并发槽 |
| RequestPermit | task/attempt/request、账号/模型快照、额度预留、执行 epoch、到期时间 | 一次请求的准入凭证，不授予工具写权限 |

SessionBinding 是持久化记录，BindingHandle 是它的受版本约束引用，不是两份真相。
本稿原称 RouteLease 的对象统一命名为 RequestPermit，避免与任务长期绑定混淆。

`quota_group` 表示真实共享计费/限流主体。同一账号的两个 Key、两个 Profile 或
两个别名不能制造两份额度。Go 与 Zen 即使共享凭证，也有不同产品路由和扣费规则。
凭证轮换保持身份时不必更换账号 ID；实际主体、组织或地域变化必须重新绑定。

## 6. OAuth 与账号生命周期

1. 用户选择 Provider、认证方法和账号别名；API Key 从安全输入或 secret-ref 获取，
   不作为普通聊天文本或命令行明文参数记录。
2. OAuth 使用 Provider 支持的授权码/PKCE 或设备流程；校验回调、state、有效期，
   支持用户取消，临时本地回调接收器完成后关闭，不成为常驻服务。
3. 校验真实账号主体、组织/空间、端点与模型权限，持久化私有凭证引用后才报告成功。
4. 同一凭证刷新采用进程内 single-flight 和跨进程排他锁，版本校验后原子保存轮换结果。
   等待者复用结果，刷新失败保持旧记录并进入需要重新登录状态，不并发刷新十次。
5. 撤销账号先停止新准入；已发请求按显式停止策略处理，未知计费仍保留，不能伪装成未发生。

凭证只在 Broker 即将发送时由受信任组件注入。连接池按账号隔离域、端点、TLS/代理和
连接相关认证配置建立；普通请求级 Token 刷新不必重建连接，具体规则由连接服务规格定义。
不得通过修改全局环境变量或共享 Authorization Header 来切换子任务账号。
导入现有配置只读源文件；不能递归搜索任意 Token，也不替其他工具刷新其所有的凭证。

## 7. 缓存亲和与会话恢复

必须区分三种缓存：

- **本地上下文缓存**：权威会话、组装结果、文件摘要等，用于可靠恢复。
- **连接/认证缓存**：HTTP 连接池、短期令牌解析结果，按身份隔离。
- **远端 KV/Prompt cache**：由厂商维护，客户端只能提供稳定输入和受支持的路由提示。

默认保持 `session/branch -> account + product + region + model + protocol` 的亲和。
系统提示词、工具定义和稳定文件前缀采用确定性顺序；任务参数、实时用量和动态状态
放在变化部分。不得为了缓存隐藏用户的有效指令、保留过时权限或阻止必要 compact。
安全和正确性优先于命中率，compact 后通常会产生新的前缀阶段。

缓存作用域至少区分租户/项目、账号身份、接入点、模型版本、协议、相关设置和前缀版本。
使用 Provider 支持的缓存键/句柄时，由适配器转换，不发送一个通用字段到所有服务。
同账号不保证命中，换账号也不能声称迁移 KV；日志区分预期亲和与实际 cached_tokens。

每个独立子会话有独立远端 session ID，不能让 100 个任务共享有状态对话链。
只有相同隐私范围内、确实相同的公共前缀才可按厂商规则共享 cache-affinity group。
无上下文依赖且输入各不相同的任务，应预期缓存收益有限，而不是先额外付费预热。

切账号或模型时：等待合法请求边界，核对未完成工具效果，从本地规范化历史恢复；
禁用不兼容的远端句柄和签名，重新验证上下文长度/工具能力，记录冷启动及绑定新版本。
停止再继续默认恢复原绑定与累计用量；原账号不可用时才按已批准策略等待或迁移。

## 8. 调度策略与配额方式分开

配额回答“能用多少”，策略回答“选择谁”。不要把贪心算法编码成一种计费单位。
下表是通过 AccountStrategy 注册的首批策略；后续算法不必修改这个核心接口。

| 策略 | 选择方式 | 适合场景 |
|---|---|---|
| pinned | 固定账号和模型，不自动切换；不足则等待/报错 | 精确控制、敏感数据、可重复执行 |
| sticky，默认 | 保留会话绑定；新任务优先偏好账号，超出允许等待或确实不可用才选其他合格账号 | 用户所说的贪心配额、长上下文交互 |
| spread | 将尚未开始的独立任务分散到有容量的账号，任务开始后仍保持绑定 | 大批独立任务 |
| auto | 先过硬约束，再根据预测等待、冷启动、成本和失败风险选路，由 Flow 提供策略参数 | 同一指定模型的自动分配 |
| remote | 一个固定远端入口负责其内部路由，zenpi 不猜测其隐藏账号 | 统一网关账号 |

Sticky 不等于把并发设为 1，也不等于把偏好账号耗尽后继续硬发请求。
Spread 不迁移正在执行的任务，不要求平均分配数量，更不能把每个 turn 轮流发给不同账号。
Remote 仍保留本地任务预算、允许的并发上限、取消和用量记录；不能将本地安全责任移交远端。

## 9. 确定性调度算法

输入为已经依赖就绪的任务，不重新实现 Goal/DAG 调度。

1. 验证任务用途、数据允许去向、模型精确约束、工具/上下文能力、账号状态、套餐资格。
2. 按原始共享限额主体去重；同一配额池的多个密钥不是额外容量。
3. 对当前绑定判断可用性和等待上限，缓存亲和不能突破硬预算或截止时间。
4. Sticky 在合格候选中优先原绑定；Spread 用剩余容量和预计结束时间分配新任务；
   Auto 对候选计算确定性评分，不调用模型选择账号。
5. 原子预留所有受影响的限额并持久化 RequestPermit；竞争失败重新读取有限次，
   不能两个调度者拿着同一份余量同时成功。
6. Runtime 执行；完成后按真实 usage 和计费规则结算，释放已确认结束的并发槽，唤醒队列。

Auto 可使用以下可解释评分，权重将不同单位归一化；不是让 LLM 猜一个分数：

```text
score = w_wait * estimated_queue_delay
      + w_cache * estimated_cold_prefill_penalty
      + w_cost * estimated_billable_cost
      + w_risk * recent_failure_risk
```

默认不因很小的评分变化切换已绑定账号：使用切换阈值和最短绑定期。
硬失败、用户显式切换及截止时间可以覆盖亲和，但不能覆盖权限与配额。
估计缺失时使用保守先验，记录缺失字段；不声称精确最优。
队列使用优先级加等待老化避免大任务饿死；重试不能无限插队，也不忙轮询或调用模型等待。
调度只唤醒现有 Runtime 中的 route-wait 状态，不新增一套提示词干预队列。

## 10. 配额账本

每个限额明确计量单位、所属主体、窗口规则、数据来源、更新时间与可信度：

- 并发模型请求数，与子智能体存活数、系统进程数分开。
- RPM、TPM、输入/输出 Token、模型调用次数、套餐 Credits、金额，各自计量。
- 滚动窗口、日/周/月重置、订阅周期及其时区，不统一伪装成“剩余 Token”。
- 本地任务硬上限、账号配置上限、Provider/组织/套餐共享上限同时成立。

额度观测标注 `remote_reported`、`locally_accounted`、`estimated` 或 `unknown`。
未知余额不是无限余额；远端报告可能滞后，也可能含其他客户端的消耗。
每份报告记录覆盖区间/游标，仅叠加报告未覆盖的本地预留和消费，不能重复扣减。
无法识别覆盖区间时保守处理，不能声称全局实时准确。

预留按输入估计与显式 max-output 上限、请求数和窗口规则计算，不预支尚未证实的缓存折扣。
每个 task 的总预算覆盖它的所有 turn、重试、规划 fork 和子任务，不能每轮重新获得完整预算。
规划在已知成本边界内申请预算；潜在无界输出必须先设置上限，不能靠事后统计限制花费。

并发只在实际请求期间占槽；等待工具或用户时保留亲和但释放已结束的模型请求槽。
关闭本地连接不一定取消远端计算，未知远端状态需保留风险占用或按适配器证实的时限收束。
已发送但没有 usage 的请求标记 `usage_unknown`，不能自动退款后再次消费同一预算。

首期对远端未知并发使用保守可配置上限。确认属于并发限流的 429 才适度降并发，
尊重 Retry-After，稳定后有限恢复；套餐耗尽则等重置或已授权路由，不使用增并发算法。
套餐降级到按量付费默认禁止；远端自身的余额回退也需显式确认，否则显示无法保证零额外扣费。

## 11. 100 个独立任务如何执行

假设 A/B/C 为三个允许该用途的真实独立额度主体，任务使用同一已验证模型，
各账号可用并发分别为 2/3/1，总任务并发上限为 6；这只是算法示例，不是厂商配额。

```text
任务池：T001 ... T100，各有独立参数、要求、输出目标、验收条件和 task_id
第一批：A -> T001,T002；B -> T003,T004,T005；C -> T006
B 先完成一个 -> 从待开始任务中认领下一个，而不是抢走 A 的运行任务
同一任务需要继续工具轮次 -> 保留原账号/模型亲和，下一请求重新预留
任务失败 -> 保留 attempt 及错误；满足安全重试规则才申请新 attempt
```

每次分发独立记录 `task_id/attempt_id/request_id/session_id/account_id/model/
policy_revision/input_digest/reservation_id/status/usage/result_ref`。
输入摘要不替代输入本身：输入或不可变引用由任务存储保存，可恢复但不暴露凭证。
结果有固定目标和幂等提交身份，不能因回调重放覆盖另一个任务的输出。

首期用有界就绪队列和容量驱动分配即可，不预先把 100 个任务锁死到账号。
仅在任务/文件确实独立或已隔离时并行；“无聊天上下文依赖”不自动意味着无文件写冲突。
交互式套餐不能因任务来自 TUI 就被当成无限批处理 API；用途判定基于实际工作负载。

## 12. 主线、Subagent 与 Flow

主线可固定账号 A/模型 X，单独子任务显式指定账号 B/模型 Y；两者共享任务预算约束，
但使用独立 SessionBinding、配置快照和并发预留，子任务不会改变主线默认账号。
所有派生仍由根宿主准入，子智能体没有递归创建或扩张账号池权限。

Flow 只产出一个受约束的路由请求，例如：

```yaml
model: coding-model-approved
accounts: batch-api-pool
allocation: spread
affinity: task
max_parallel_tasks: 6
fallback_model: deny
paid_overage: deny
```

以上是待实现的类型化配置，不是已实现命令。Flow 可以建议候选模型、用途和权重，
宿主取它与用户许可的交集；模型不能查看 Token、临时加入新账号、放宽预算或改用途标签。
`auto` 指定模型时只选账号；跨模型降级必须另外授权，不能藏在自动算法里。

## 13. 交互约定

以下是拟定入口，最终语法与现有 auth/Profile 命令统一迁移，不维持两套配置真相。

| 操作 | 用户看到的行为 |
|---|---|
| `/account` | 列出脱敏别名、Provider/套餐、认证状态、可用模型、绑定和额度可信度 |
| `/account use <alias> --scope session` | 默认范围；在下一个安全请求边界切当前会话，显示缓存/费用影响，不改运行中的子任务 |
| `/account use <alias> --scope default` | 只影响后续新会话，当前会话保持原绑定 |
| `/route <policy> [--task <id>]` | 修改指定范围的路由策略；已经发出的请求不变，硬约束不放宽 |
| `/route explain [task-id]` | 显示为何选中/排除账号、为何等待、预期缓存影响，零模型调用 |
| `/quota` | 展示已用、预留、未知用量、窗口重置和当前并发；远端未知则明确显示 |
| 添加/登录账号 | 安全输入或浏览器流程，不把凭证提交到模型 |
| 禁用/移出池 | 停止新路由，保留审计；受影响会话等待或按已授权策略迁移 |

改配置先验证再提交；失败保留旧配置和当前进度。
默认先做本地验证；需要计费探测的验证操作必须明确提示，禁止配置时偷偷调用所有模型。
配置热更新采用版本号，执行记录保存实际生效版本，TUI/headless 使用同一控制入口。

## 14. 异常、停止和恢复

| 情况 | 处理 |
|---|---|
| 401/凭证过期 | 允许刷新时单次刷新；再次失败转需登录，不无限轮换账号 |
| 403/用途或权限拒绝 | 不通过换账号逃避拒绝；检查模型资格和策略 |
| 429/并发或窗口额度 | 类型化区分；遵守退避或重置时间，无权解析时保守等待 |
| 超时/断流且已产生输出 | 保留部分输出和尝试身份，不能静默换账号重放工具副作用 |
| 模型/协议不兼容 | 发出请求前拒绝；不把未知字段悄悄丢掉 |
| 用户 Esc 停止 | 按共享干预契约停止根执行，冻结路由；账号可用不触发自动复活 |
| continue/继续 | 从检查点恢复，保留预算与原亲和；重新检查资格并产生新执行 epoch |
| 重启/租约过期 | 重建未结算记录；先核对旧执行与未知效果，不凭超时重新派发已发送任务 |
| 账号池变化 | 只重算未开始任务；正在运行的任务按已捕获配置结束或明确取消 |

所有重试由 Gateway 的一个尝试策略统一管理，适配器不能另做隐藏重试，
避免“账号数 × 协议重试 × Runtime 重试”放大调用量。重试计入同一 task 的预算。
本地幂等键不保证远端不重复计费或不重复执行，重试许可必须依据已知远端语义。

## 15. 持久化与跨进程边界

账号元数据和凭证各有唯一所有者；任务会话保存路由事件，不复制明文凭证。
沿用现有持久化机制，增加一个有界、受锁保护的共享额度登记面作为跨会话准入真相，
而不是让每个 Session 各自认为账号额度完整可用。它属于现有 Quota Owner 的扩展。

同一机器多个 CLI 经 IPC 接入唯一 Broker；共享状态由服务单一 owner 和 journal writer
提交，客户端不直接争写文件。模型预算、账号预留及绑定接受由服务统一提交，客户端
Session 保存 receipt_id 投影，不构造虚假的跨文件原子事务。先持久化预留和发送授权，
才允许发送；崩溃窗口状态不可确认时保留 unknown，
等待核对或人工明确处置。终态迟到时按 task/attempt/epoch 验证，不能完成新尝试。

首期不承诺多机器全局强一致配额。多机器共享同一账号时，使用已授权远端调度器
或显式分配不重叠的本地预算，不能依靠独立 JSON 文件声称全球配额已受控。
本地数据库仅在文件锁/恢复成本有测量证据时再讨论，不是本轮默认依赖。

## 16. 冲突与实施顺序

硬冲突：一个 Provider 一个 wire_api 无法覆盖混合协议目录；按协议标记全部能力
不足以证明模型能力；只在启动时绑定一个后端无法支持独立子任务账号；会话内预算
不足以约束跨会话共享账号。分别用模型级路由、能力交集、请求快照和共享额度准入解决。

软冲突：缓存亲和与吞吐/截止时间取舍，用显式策略和切换回执解决。
伪冲突：账号路由不是第二个 DAG 调度器；OAuth 登录也不是推理协议。
套餐用途限制是真实准入条件，不通过改提示词、客户端标识或增加密钥绕过。

推荐分阶段交付：

1. 固定 AccountScheduler 的 bind/acquire/settle/rebind/cancel/explain 边界，
   明确账号/产品/模型身份，兼容读取旧 Profile，统一默认协议行为。
2. 固化规范化请求/事件边界，补全 Chat 流式和 Messages，再接 Google 模型。
3. 接入 API Key Provider 预设、模型目录和资格验证；OAuth 按独立授权证据交付。
4. 先实现 pinned/sticky、多账号隔离、共享额度预留与重启恢复。
5. 接入独立子任务 spread、Flow 路由参数和可解释 auto；remote 使用同一入口。
6. 完成真实端点验收、费用/缓存观测和 TUI/headless 交互，不以配置成功代替可用。

每阶段维持一个集成所有者；拆分文件时保留现有 Backend 调用兼容，不增加全局可变
账号单例。账号调度内部按规格稿 S0-S5 实施，不以新增协议接入替代准入验收。
回退保留身份、会话和未结算账目；先停止新准入并核对，不恢复可绕过配额的旧发送
路径，不让不兼容二进制写入新记录。具体兼容与回退门槛由规格稿统一规定。

## 17. 必须通过的验收

- Goal、普通会话、Flow、Subagent 和批量任务共用 AccountScheduler，没有旁路选账号。
- 新增测试策略只改实现、注册和测试；无需修改 Loop、协议适配器或额度所有者。
- 所有策略共用资格、配额和取消契约测试；非法候选、陈旧快照和未知策略版本拒绝执行。
- 绑定不占请求槽；工具等待时保留亲和；每次模型调用和重试必须有单独 Permit。
- 等待项可取消且有界；重复请求不重复排队；Permit 消费与停止竞态不能重复派发。
- 同一账号两把 Key 不增加总额度；两个进程争最后一个并发槽只能一个成功。
- OAuth 并发过期只刷新一次；过期回调和重复登录不能覆盖新凭证。
- 主线 A、子任务 B 的认证头、会话和连接池不串用，B 的切换不改变 A。
- 相同上下文的绑定稳定；实际命中与未知命中分开计量；不承诺跨账号 KV 迁移。
- 100 个独立任务每次分发有独立记录，达到并发上限但不越界；完成顺序可乱，结果不串。
- 不允许批量的套餐在准入时被拒绝；无授权不跨计费产品或切模型。
- 停止/恢复、compact、断流、未知 usage 和崩溃重放不导致重复任务效果或预算退款漏洞。
- 协议一致性测试覆盖文本流、拆分工具参数、工具续接、图片、错误、usage 和取消。
- 调度、排队、限额刷新和解释路由不产生额外模型调用；调用数按 task/attempt 核算。
- Gateway 为唯一重试所有者；用例验证多账号故障不产生重试乘法或 429 请求风暴。

验收记录至少包含账户切换次数、实际缓存读 Token、首 Token 延迟、排队时间、
预估/实际用量差、未知用量数、重复执行数和最大实际并发；缓存不可见时记 unknown。

## 18. 发布资格边界

默认 sticky，批量显式 spread，auto 不换模型，套餐不自动转按量付费。
OAuth 集成和具体套餐必须在发布前提供授权、地域、协议及用途验证；这些信息影响接入资格，
不影响上述统一抽象和调度算法。未确认的 Provider 能力保持 disabled/unknown，
不能为了填满支持列表而列为已实现。
