# 117 单次分段诊断：主控独立复核

正式冷启动预算仍失败。此次私有诊断把一个新的执行实例中最大的耗时区间定位到父端开始启动至 Rust main 首次取时之间：1096.025ms；M0–M8 内部40.610ms；M8 至父端 wait 返回0.933ms，总计1137.568ms。它没有确定具体根因，不支持将时间归因于代码签名、系统策略、加载器或某个产品初始化函数，也不允许扣除该区间重新计算原预算。

主控独立读完 diagnosis.md、完整五文件 diagnostic.patch（包括42行记录模块和main修改）、完整 launch-once.py、真实 launch.run.json 和全部9行原始标记，以及完整 verify.py。额外顺读私有 core6065–6140、headless4490–4520/4720–4770/5060–5090/6320–6355、两个缓存响应写入函数。巨大core/headless文件及整个SDK/libc源码未在此处重新全读；归档完整源码只作身份保存。主控没有执行任何诊断、生产二进制、构建、PTY或旧工作流脚本。

M0首先调用clock_ns，早于main中其它显式产品调用，但不等于OS exec或第一条机器指令。记录模块在标记点采用固定9槽，系统时钟成功后记录线程ID，无文件输出和动态缓冲。M8之后才向专用create_new文件写出记录。父端显式clock_gettime_ns(CLOCK_MONOTONIC)，子端libc相同常量与纳秒换算；原始计数无时钟/线程错误，各标记恰一次。PID99639的ppid99638对应Popen返回的time包装器PID；标记同一线程30184765、顺序递增且在父观察区间内。独立完整性核验重新计算全部10个差值及首尾和，值一致。

M4只是在owner初始化和spawn调用之后，不是后台线程已ready。M5在主线程识别Shutdown并设置stopping之后，不是stdin首次读取时刻。M6在实际write_cached_versioned_response返回之后；已读函数链包含remember_terminal、output.write_all与flush，故该标记晚于成功写出。M7在shutdown_and_join及replay/owner关闭闭包返回之后；这不推导其它负载下每一个可能被分离的线程都已退出。此实例成功返回，不能代替完整生命周期验收。源级标记位置与读到的控制流支持上述阶段解释。

父端Popen后写入原来的一条shutdown JSONL并关闭stdin，随后用selector收集stdout/stderr/EOF和退出；原预算使用communicate，二者不是完全相同的观察实现。新增标记、专用文件写出及不同二进制也可能扰动结果。启动前的1096ms仍包括time包装器、调度、映像加载和Rust main之前的执行，缺少目标exec及调度事件锚点。父端首读在M6后约0.046ms只是观察时差，不是精确传输耗时。5秒watchdog未触发，time包装器wait返回0；stdout144B为同一条closing/drained成功响应，与三个生产样本相同。
