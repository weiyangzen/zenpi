## 2. 第 2 轮：授权审计账本（authorization ledger）

### 2.1 现状事实（已核实）

审批相关的 journal 事件现在有 **三条**，schema 互不一致：

| 事件 | 位置 | 何时写 | 带哪些字段 |
|---|---|---|---|
| `approval_resolved`（宿主路径） | `src/core.rs:5396` | 策略**没有**短路（请求真的进入 pending），宿主回答之后 | `request_id` `turn_id` `call_id` `tool` `side_effect` `origin` `policy_digest` `lease_id` `preview` `decision` `remember` `execution` |
| `approval_consumed`（宿主路径） | `src/core.rs:5424` | 上一条之后紧跟 | 上条的**子集** + `execution`，无 `side_effect`/`origin`/`policy_digest`/`lease_id`/`preview` |
| `approval_resolved`（worker 路径） | `src/core.rs:5458` | 策略判定为 `WorkerAllowAfterPreflight` 且预检通过 | `request_id` `turn_id` `call_id` `tool` `decision` `remember` `source` `policy_digest` `execution`——**有 `source`**，但**没有** `side_effect`/`origin`/`lease_id`/`preview` |

关键事实：**上面三条全部写在 `if approval.is_none()` 块内**（`src/core.rs:5342`–`5455`）。
策略若在 `decide_after_preflight`（`src/approval.rs:510-540`）里短路返回 `Some(...)`——
即 `side_effect == ReadOnly`、`per_tool` 命中、`TrustedWorkspace` 命中、`Never`——
**一条事件都不写**，工具直接执行。

其它相关事实：

- `policy_digest` 是 64 位小写 hex（`src/approval.rs:76` 校验），sha256。
- 恢复路径**已经在从 journal 读这些事件**：`with_remembered_events`（`src/approval.rs:542+`）
  只接受 `type == "approval_resolved"` 且 `remember == true` 且
  `origin ∈ {agent_tool, user_shell}` 的事件来重建「记住的授权」。注意它**没有读 `source`**，
  是用 `origin` 近似。
- `--auto` 的实现是「把 owner 的策略设成 `Never`」（`src/core.rs:7955`），
  `Never => Some(Allow)` 在 `src/approval.rs:537`。
- 「全放行」的语义按设计要求**保留策略、闸门与审计事件**（`src/core.rs:7951` 的注释这么写），
  但按上面的事实，**审计事件恰恰没有保留**。

### 2.2 问题

**问题 2.1｜记录的边界：** 授权的判定应该**每次都记**，还是只记「人工做过的决定」？
请给判据。特别地：如果一次 turn 里有 40 次只读工具调用，全记会不会把 journal 淹掉、
反而降低可回溯性？如果可以聚合，**聚合的边界**在哪——什么信息一旦聚合就再也答不出
「这条命令当时为什么被放行」？

**问题 2.2｜判定与消费：** 「授权结果」与「执行结果」要分开记录。分开到什么粒度？
一个 `request_id` 对应的事件序列应该是什么形状——判定一条+消费一条，还是判定时就带上执行证据？
后者会不会让「批准了但没执行」变得不可表达？请给出事件序列的**不变量**。

**问题 2.3｜策略版本：** 现在记的是 `policy_digest`。但 digest 是单向的，跨版本不可比——
事后拿到一个历史 digest，无法知道当时命中的是哪条规则。应该记 digest，还是记**可读的策略快照**，
还是两者都记？如果两者都记，快照里能不能出现工具名与参数（有泄漏风险）？

**问题 2.4｜命中规则的表达：** 「命中规则」怎么写才是**稳定**的？规则集会演进，历史事件要能自解释。
用枚举字符串（`per_tool_grant`）会不会在规则集扩展时变成谎话？用结构化规则 id + 版本号呢？
请给出一个不会随时间腐坏的表达方式。

**问题 2.5｜remember 的归属：** 「记住我的选择」产生的授权，跨会话存活。
它算**人工批准**还是**自动放行**？重启后它还有效吗？如果有效，重启后那条工具调用的审计记录里，
「谁批准的」应该写什么——写当初那个人，还是写「来自某条 remember 规则的自动放行」？

**问题 2.6｜三条事件 schema 的统一：** 给出现状的**最小统一 schema**：
哪些字段是所有授权事件必须有的，哪些是特定来源才有的？`source` 字段应该成为必填吗？
现有那条 worker 路径事件带 `source` 而宿主路径不带——这个不对称应该往哪边收？

**问题 2.7｜可见性：** 审计事件应该对谁可见？模型（不应该吧）、客户端（headless 的 capability？）、
还是只落盘？请给判据，并说明「对客户端可见」会不会反过来变成一种信息泄漏侧信道。

## 3. 第 3 轮：同步内核里的等待语义与失败模式（Rust 特有）

### 3.1 现状事实（已核实 + 推断）

**已核实：**

- 协调器内部是 `Arc<(Mutex<CoordinatorState>, Condvar)>`（`src/approval.rs:132`），
  与 `Mutex<Agent>` 是**两把无关的锁**。
- 等待循环（`src/approval.rs:225-250`）：
  ```
  loop {
      查 cancelled() → 清理并返回 Err(Cancelled)
      查 decisions  → 命中则清理并返回 Ok(response)
      wait_timeout(50ms)   // 释放状态锁
  }
  ```
  即**带超时的轮询**，每轮重新检查状态——所以虚假唤醒不会放行。
- `has_pending()` 在 mutex **poisoned** 时返回 `true`（fail-closed），注释说明它被用作
  连接选择的栅栏（`src/approval.rs:262`）。
- `respond_with_request` 对未知或已回答的 `request_id` 返回 `UnknownRequest`，**不缓冲**
  （`src/approval.rs:312+`）。
- `WorkerAllowAfterPreflight` 的 worker 决策**不允许**变成 remember 的授权，直接报错
  （`src/approval.rs:337`）。
- 取消用 `cancellation_epoch()` 比较（`src/core.rs:3497`）。
- 等待期间还会 poll 输入队列（`InputPump`，`src/core.rs:5369`）。
- **推断（未做运行时实验）**：owner pool 用 `try_lock` 判忙（`src/project_workspace.rs:736/765/773`），
  且审批等待发生在 turn 内部 → 一个 owner 等审批时**持有自己的 `Mutex<Agent>`**。
  请把这条当作待验证前提来用，并在结论里说明「如果这条成立 / 不成立」分别意味着什么。

### 3.2 问题

**问题 3.1｜等待期间该持有什么锁：** 给出一条不变量，划清「阻塞等待时**必须**释放的锁」
与「可以持有的锁」。判据是什么——是「宿主推进是否需要它」，还是别的？
如果一个 owner 在等审批时确实占着自己的 `Agent` 锁，哪些宿主操作**必须**仍然可用
（回审批、取消该 owner、关闭该项目、切换到别的项目、读该 owner 的状态）？请按「必须有 / 可以没有」分类。

**问题 3.2｜释放之后如何证明状态没变：** 如果结论是「必须释放 `Agent` 锁」，
那么被唤醒后如何证明这期间状态没有被改（审批策略被换、连接被切、owner 被重建）？
给出可操作的复检骨架——用 epoch、lease、revision 还是 digest？哪个是**充分**的？

**问题 3.3｜poison 的方向：** 现在 `has_pending` 在 poisoned 时返回 `true`（fail-closed）。
这个方向对吗？poison 之后这个 owner 应该**永久不可用**（后续所有工具都拒绝），
还是**可恢复**（重建协调器）？两种选择的失败模式分别是什么？请选一个并给判据。

**问题 3.4｜轮询 vs 精确唤醒：** 50ms 轮询避免了丢唤醒，代价是延迟与 CPU。
给出判据：什么条件下轮询可接受，什么条件下必须精确唤醒？如果改成精确唤醒，
需要同时满足哪些条件才不会引入丢唤醒？

**问题 3.5｜取消与回答同时到达：** worker 判断 `cancelled()` 后清理 pending 并返回 `Cancelled`；
但宿主可能**正好在此时** `respond` 了一个决定。给出「取消与回答同时到达」的裁决规则：
谁赢？被丢弃的那个决定需要被记录吗？会不会出现「宿主以为批准了、实际没执行」的静默丢失？

**问题 3.6｜嵌套审批：** 一个正在等审批的工具执行，能否再触发另一个需要审批的工具？
在这个架构里会不会自死锁？如果不能，这条限制应该由**类型**表达还是由**运行时**检查表达？

**问题 3.7｜无 GC 的悬空：** 列出在这个架构里「审批请求被 drop 但 worker 还在等」可能发生的路径。
能不能用所有权/类型在编译期排除掉大部分？给出「能靠类型排除的」与「只能靠运行时兜底的」分界。

## 4. 第 4 轮：多 owner 并发审批与重启隔离

### 4.1 现状事实（已核实）

- 每个 owner 有**自己的**协调器实例；没有全局的审批仲裁者。
- `request_id` 是 `approval-{sha256(编码后的 session_id + turn_id + call_id + policy_digest)}`
  （`src/core.rs:6451`）。
- 宿主（TUI / headless）通过 `drain_pending()` 把待审批请求变成 `approval_request` 事件；
  `drain` 只把请求标记为 visible，**不删除**（`src/approval.rs:269`）。
- 已回答的请求从 pending 移除，重复回答返回 `UnknownRequest`。
- 重启恢复靠 journal 重放 + `with_remembered_events` 重建「记住的授权」。
- pool 在回收 owner 时，`try_lock` 失败会**保留**该 owner 而不是丢弃（`src/project_workspace.rs:765`）。

### 4.2 问题

**问题 4.1｜多 owner 仲裁：** 两个 owner 同时有待审批请求，宿主该按什么顺序呈现？
全局 FIFO、按 owner 分组、还是让客户端自己选？TUI（单屏）与 headless（多路复用）是否应该有不同的顺序契约？
请给判据，并说明「顺序」是不是一个应该进契约的东西——还是纯呈现细节。

**问题 4.2｜等待中的 owner 可被如何处置：** 一个 owner 正在等审批时，
「切换到别的项目」「关闭该项目」「取消该 owner 当前 turn」这三件事各自的正确语义是什么？
哪些应该立即生效、哪些应该被拒、哪些应该先撤销审批再执行？
请特别注意「关闭一个正在等审批的项目」——那个审批请求该变成什么状态？

**问题 4.3｜重启隔离的粒度：** 「旧审批不得作用于重建后的 owner / 任务」——
身份校验用 `session_id`、owner 实例 id、`turn_id` 还是它们的组合？
现在 `request_id` 是这几个值的哈希，所以**重建后如果 turn_id 与 call_id 复用，会不会算出同一个 id
从而误接受**？请给出身份的**最小充分集**，以及需不需要加一个「owner 实例随机数」作盐。

**问题 4.4｜有效期：** 审批该不该有有效期？如果有，超时后是「拒绝」还是「变回待审批」？
对一个停机两天后重启的会话，一条 48 小时前的待审批请求应该怎样处理才是诚实的？

**问题 4.5｜迟到回答：** 现在迟到/重复的回答返回 `UnknownRequest`（拒绝，不缓冲）。方向对吗？
如果客户端因为网络分区重连后重发同一个回答，用户体验上会不会「明明点了允许却没执行」？
请给出一条同时满足「不误解」与「不静默丢失」的规则。

**问题 4.6｜跨 owner 的 remember：** 「记住我的选择」是记在 owner 上还是会话上？
如果一个用户在 A 项目里记住「允许 `user_shell`」，打开新的 B 项目时这条记忆应该生效吗？
